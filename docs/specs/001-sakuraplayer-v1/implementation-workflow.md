# SakuraPlayer 实施与验证工作流

**生效日期**: 2026-07-25

**状态**: Accepted

**适用范围**: 所有未完成的 `TASK-xxx`、缺陷修复和任务内评审修复

**治理依据**: [实施验证门禁优化](changes/2026-07-25--implementation-verification-gates.md)

## 1. 目标与不变量

本流程减少重复构建、重复启动完整 Compose 和审计过晚造成的返工，但不降低任何任务的 Definition of Done、验收条件或最终测试范围。

- 正式范围、依赖和验收以当前 `tasks/TASK-xxx.md` 为准。
- 快速门禁只缩短实现反馈，不是完成证据，也不能替代最终门禁。
- 每个正式任务仍独立完成、独立更新状态和交接、独立创建中文 Git 提交。
- 默认测试不得访问真实 115、JavDB 写操作或付费 AI；外部门禁仍只在指定 E2E 任务显式运行。
- 共享工作区采用单写者：主实施路径负责文件、数据库、容器和 Git 变更，子智能体只做并行只读审计。

## 2. 开始前的规模检查

读取依赖、验收条件和 Definition of Ready 后，把任务拆成可独立验证的实现批次。批次只是当前 `TASK-xxx` 内的执行顺序，不产生额外提交，也不改变任务边界。

建议每个批次只覆盖一个行为闭环，例如“领域规则 + 仓储 + 对应测试”或“接口映射 + 契约测试”。任一情况出现时，在写代码前评估是否需要正式拆分任务：

- 同时修改三个以上限界上下文或客户端 feature。
- 同时包含数据库迁移、公开契约、外部适配器和调度/后台执行中的三个以上类别。
- 无法为主要行为建立相互独立的聚焦测试。
- 预计一次评审无法清楚判断所有安全边界和失败分支。

若必须改变正式任务边界，应先创建变更规格，再同步任务索引、依赖、AC 映射和追踪矩阵。不得用 `.planning/` 或临时批次静默替代正式任务。

## 3. 标准执行顺序

### 3.1 准备

1. 按 `AGENTS.md` 读取交接、架构、功能规格、技术计划、当前任务及直接契约。
2. 检查 `git status --short`、最近提交和任务真实状态，保护不属于当前任务的工作区内容。
3. 对超过 5 次工具调用或多阶段任务建立 `.planning/TASK-xxx/`，记录阶段、发现和验证结果。
4. 列出实现批次、风险边界、聚焦测试和最终门禁，确认 Definition of Ready 满足后再修改文件。
5. 涉及行为契约、Schema、OpenAPI、错误码或数据结构时，在进入 Fast 前完成同步；不能把行为文档修改留到 Final 之后。

### 3.2 测试驱动实现

每个实现批次按“失败测试 -> 最小实现 -> 聚焦回归 -> 重构”的循环推进。只运行受影响的单元、契约、静态检查和必要的 PostgreSQL 集成测试；测试失败时先定位根因，不扩大跳过范围或降低断言。

### 3.3 快速门禁

所有实现批次完成后，运行与本任务相关的最大合理测试子集：

| 内容 | 要求 |
|---|---|
| 自包含测试 | 受影响的 start、unit、API、契约与安全测试 |
| PostgreSQL | 涉及迁移、约束、事务、锁或 PostgreSQL 方言时必须运行聚焦集成测试 |
| 静态检查 | 当前语言的格式、lint、类型或构建检查 |
| 差异检查 | 阅读完整 diff，运行 `git diff --check`，检查秘密和未跟踪资料 |

快速门禁失败时继续在实现循环中修复，不启动完整 Compose。

### 3.4 最终审计

快速门禁绿色后再进入最终审计。主实施者先检查完整差异；多个子智能体可并行执行 Schema/仓储、API/安全和代码质量只读审计，并返回具体文件、行号、严重级别和建议。

- 子智能体不得写文件、运行迁移、管理共享容器、暂存或提交。
- 主实施者复核审计结论并统一修改。
- 所有 P0/P1 必须关闭；P2 必须修复或记录不阻塞的明确理由。
- 审计修复后重新运行受影响的快速门禁，直到结果收敛。

### 3.5 最终门禁

只有任务实现、快速门禁、完整 diff 和最终审计都收敛后，才进入最终门禁。

| 内容 | 要求 |
|---|---|
| 完整自动测试 | 运行当前任务要求的完整测试集合，不以聚焦测试代替 |
| 真实 PostgreSQL | 从受控测试入口验证迁移、约束、事务和恢复 |
| 完整 Compose | 构建并启动所需服务，验证迁移、健康、canary、秘密扫描、重启、降级恢复和资源清理 |
| 客户端/外部门禁 | 只在对应任务要求时执行 Windows、HarmonyOS 或真实 115 门禁 |

完整 Compose 在每次最终门禁尝试中最多运行一次。若失败，本次最终门禁立即结束；修复后必须重新通过受影响的快速门禁和审计，再发起新的最终门禁尝试。任何生产代码、测试、迁移、配置、运行脚本或行为契约在最终门禁后发生变化，都会使原结果失效。

### 3.6 完成与提交

1. 更新任务状态、勾选项、实现证据、追踪矩阵映射元数据和 `SESSION-HANDOFF.md`；行为契约必须已在 Final 前同步。
2. 再次检查完整差异、`git diff --check`、秘密、未跟踪文件和最终门禁证据。
3. 只暂存当前任务相关文件，创建一次中文 Git 提交。

### 3.7 任务状态

| 状态 | 进入条件 |
|---|---|
| `pending` | 尚未开始，Definition of Ready 未确认或依赖未满足 |
| `in_progress` | 依赖和 Definition of Ready 已确认，任务正在实现或运行 Focused/Fast |
| `implemented` | 任务范围已实现且 Fast 绿色，等待完整只读审计 |
| `reviewed` | 审计问题已处理，受影响的 Fast 已重跑，允许进入 Final |
| `completed` | Final 绿色，任务勾选、证据、追踪矩阵和交接已同步，可创建当前任务提交 |

状态不得跨级用于绕过审计或 Final。E2E 和清理任务依赖“已完成”的前序任务时，前序任务必须是 `completed`，不能只凭聊天记录或 `implemented` 推断。

## 4. 后端测试分层

后端命令和当前脚本能力以 [backend/tests/README.md](../../../backend/tests/README.md) 为准。

| 层级 | 反馈目标 | 基础设施 | 用途 |
|---|---|---|---|
| Focused | 分钟内 | 复用依赖镜像，挂载当前源码 | TDD 和单个实现批次 |
| Fast | 短反馈 | 自包含测试；需要时复用专用 PostgreSQL 进程，每次创建隔离数据库 | 进入最终审计前 |
| Final | 完整证据 | 隔离 Compose 项目和新数据库卷 | 任务完成与提交前 |

复用 PostgreSQL 只允许复用测试进程和依赖镜像，不得复用测试数据库事实。每次测试必须使用唯一数据库名，在 `finally` 中删除；不得连接开发或生产数据库。中断残留只能按当前测试运行 ID 定向清理。

## 5. Docker 缓存约束

- 依赖描述文件和依赖安装层必须位于源码复制层之前，源码变化不应触发依赖重装。
- BuildKit/pip 缓存可以跨测试运行复用，但不得包含 secret、测试数据库或应用状态。
- 快速测试使用只读挂载的当前仓库内容，避免因镜像内旧源码产生假绿色。
- 最终门禁必须清理临时容器、网络、卷和 secret；可保留共享依赖镜像与无秘密的构建缓存。
- 依赖文件、Dockerfile、基础镜像或锁定工具版本变化时必须重建依赖镜像。

当前 `run-compose.ps1` 仍是 Final 入口，尚未提供 `-Gate Fast` 参数；不得在文档或交接中把未实现的脚本接口写成已通过能力。脚本拆分完成前，Fast 使用测试 README 中列出的现有命令组合。

## 6. 证据记录

`SESSION-HANDOFF.md` 只保留当前任务恢复所需的三项门禁状态：当前阶段、最近绿色快速门禁摘要、最终门禁状态。详细命令、失败和修复过程写入 `.planning/TASK-xxx/progress.md`，最终提交事实以 Git 和任务文件为准。
